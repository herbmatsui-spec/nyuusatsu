## 目的・境界・依存関係

- 目的: 入札検索を安定動作させ、同じ検索条件を保存検索・モバイル・APIから再利用できるようにする。
- 既存対象: `app_unified_search.py`、`services/search_service.py`、`tests/unit/test_search_service.py`、`tests/unit/test_unified_search_ui.py`、`static/css/custom_unified_search.css`。
- 新規予定: `services/search_criteria.py`。条件定義が他計画で追加済みなら同一ファイルを再利用し、別の定義を作らない。
- 対象外: Flask管理画面の置換、全文検索エンジン刷新、認証基盤の新規開発、全件Excel出力。
- 改善案04がアクセス範囲の定義を所有する。未完成ならテスト用に注入して作業できるが、認可なしで公開しない。
- 改善案03が落札画面、06が抽出条件・表示、02が保存検索、05がモバイル、07がHTTP連携を所有する。共通ファイルを同時編集しない。
- 推奨順: テスト隔離 → 04のアクセス契約 → 01 → 03/06 → 02 → 05 → 07 → 09。08は独立して進められる。課金の本番有効化はこの順序とは別の承認事項。

## 固定する検索契約

`SearchCriteria` v1の基本項目は `keyword`, `exclude_keywords`, `use_or`, `prefecture`, `organization`, `bid_type`, `announcement_from`, `announcement_to`。都道府県は2桁文字列の配列。`budget_min`, `budget_max`, `qualification_keywords`, `deadline_from`, `deadline_to`, `deliverables_keyword`, `sort_column`, `sort_direction` もv1初版から受け入れる。現行UIが既にこれらを送信しており（`app_unified_search.py:65-72`）、既存 `services/search_service.py` の意味を保持しないと01完了時に既存検索が壊れる。厳密な検証・同義語展開・表示の所有は改善案06に残す。

含む語は空白区切りのANDまたはOR、除外語はいずれかに一致した案件を除外する。含む語と除外語は併用できる。旧 `use_not=True` は旧keywordを除外語へ移す互換変換とし、未知キーはエラーにする。SQLの `%` と `_` は通常文字として扱う。

レスポンスは既存の `results`, `total`, `offset`, `limit` を維持。アクセス主体・許可地域は検索条件やクライアント入力から作らず、認証済みコンテキストから別に受け取る。地域未選択は「許可された地域全部」であり「全国無制限」ではない。

各ステップは作業とそのテストまで終えてから次へ進む。以下の工数は環境準備・レビュー待ちを除く目安で、合計24〜42時間。未確認の関数やライブラリを推測して補わない。

- 確認: 空DB、1件DB、21件DBで実行し、作業DBや外部通信を使用しない。ソート修正後の結果を確認し、まだ失敗する場合だけ失敗として記録する。
- 完了条件: 実装対象をモックせずSQLを検査できる隔離テストがある。
- 工数目安: 2〜4時間。

### ステップ 2: SQLAlchemyのソート修正を回帰テストで保護する
- 対象: `services/search_service.py:107`、`tests/unit/test_search_service.py`。
- 作業: 現在の `.asc/desc().nullslast()` を保持する。NULLは両方向とも最後、同値idは主ソートと同方向という既存契約を固定する。旧NULL先頭の期待値が残っていれば契約に合わせる。
- 確認: 値がNULL・100・200・100の4件で両方向のID順を確認する。検索結果0件でも例外が出ない。
- 完了条件: キーワードなしの基本検索からTypeErrorがなくなる。
- 工数目安: 1〜2時間。

### ステップ 3: 検索条件を一つの型にまとめる

- 確認: 空条件、2都道府県、誤った地域コード、未知キー、上限超過、現行UIが送信する全項目を入力し、正常化結果または明示的な検証エラーを確認する。
- 完了条件: UI・保存検索・APIが参照する唯一の条件定義になり、01適用後も現行検索が動作する。
